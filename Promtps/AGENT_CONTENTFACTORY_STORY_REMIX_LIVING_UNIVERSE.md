## 4. Living Universe persistent data model (system of record)

Use repo-native persistent DB if it already exists; **SQLite is acceptable for local single-host operation** with WAL/transactions, but first inspect current DB patterns and avoid duplicating the source of truth. Excel is **import/export/review artifact**, not authoritative mutable DB in concurrent jobs. Seed universe empty by default. Add versioned schema/migrations and documented export XLSX in repo-compatible locations.

Minimum entities and suggested fields (adapt naming to code conventions):

1. `characters`: stable `character_id` (UUID or durable ID), display_name, aliases, core_personality, temperament, motivations, strengths, flaws, communication style, boundaries/constraints, genre affinities, visual/voice cues where useful, origin=`original_generated|user_created|approved_import`, status=`active|archived|staged`, revision, timestamps. **Do not globally attach one story's death/job/romance/canon outcome.**
2. `role_types`: stable role keys (protagonist, deuteragonist, antagonist, rival, foil, mentor, ally, love_interest, confidant, comic_relief, catalyst, gatekeeper, wildcard, etc.); role is assigned per story and multiple compatible roles can coexist.
3. `worlds`/`story_realities`: `world_id`, `story_id`, timeline/canon policy, genre/context, world constraints. Under `parallel` outcomes don't cross worlds.
4. `story_cast`: `story_id`, `world_id`, `character_id`, `variant_id`, `role_code`, relevance and fit notes, local name alias if explicitly allowed, character-specific goals/arc, lock status.
5. `story_relationships`: scoped to `story_id`+`world_id`, endpoint character IDs, type, direction, status, timeline, evidence; relationships **do not automatically become global canon**.
6. `character_variants` (AU): character ID + world/story, local facts and controlled deviations; stable core traits not overwritten by role changes.
7. `appearances` / `character_story_history`: story, role, outcome, engagement notes, date, cast snapshot; keeps candidate vs approved separate.
8. `character_candidates` / `universe_change_sets`: generated identities and planned updates staged per job until QA accepted.
9. `universe_revisions` + `audit_events`: who/what changed which fields, before/after, job id, publish id, UTC timestamp, rollback/replay reference.
10. `config/presets` and per-job resolved snapshot: validate values server-side; preserve old-mode defaults.

### Autonomous casting algorithm (contract)

1. From original premise/outline infer role slots, required skills, compatible traits, genre/world constraints and relationship structure.
2. Query eligible ACTIVE characters; exclude archived, logically impossible or prohibited candidates; rank explainably on role fit, continuity/core constraints, story cast diversity and genre. **Reuse strategy `reuse` sets a positive preference, not a hard quota.** Avoid overuse of the same cast if it damages story quality.
3. Validate the complete ensemble (not just independent top picks): believable contrasts, antagonist strength, goals/relationships, cast size, distinct voices, role coverage, no identity contradiction. Re-rank when two candidates conflict.
4. For unfilled roles, invent fully original characters with unique IDs, new personality/motivations, distinct narrative function; check duplicates / near-identical existing profiles, stage additions only.
5. Freeze approved cast snapshot before expensive chapter write. All writer prompts use canonical IDs and approved story-specific labels, never unconstrained spontaneous main-character substitutions.
6. If outline changes significantly, allow one bounded recast with explicit revision and rerun only dependent steps. Never leave orphaned relationship IDs.
7. On passed, accepted story: transactional idempotent publish of new originals, appearances and story-scoped relationships. On failure or retry: stage remains unchanged or rolled back; on job rerun same `publish_id` is a no-op.
8. If universe still empty: create the necessary **smallest viable cast** automatically. No mandatory 48-person seed, no forced user intervention.
